# Рецепты смок-тестов без фреймворка (оба проходят гейт в обычном `.mjs`)

Сам `.mjs` — чистый JavaScript: контракт проекта — **без TS-аннотаций**
(`const x: any[]`, `x as any`, типизированные параметры), которые выглядят безобидно,
раз импортируемый файл — TypeScript. Типы остаются на стороне импорта
(`import './hooks/x.ts'` из `.mjs` работает), а проверки пишутся через факты:
`JSON.stringify`, `typeof`, `.length`.


## Next-роут напрямую, без сервера и без HTTP

Вызывай exported `POST` с мок-запросом:

```js
const { POST } = await import('./app/api/mcp/call/route.ts');
const req = { headers: new Headers(), json: async () => ({ name: 'get_levels', arguments: { x: 1 } }) };
const res = await POST(req);            // NextResponse: .status, .json()
```

- Auth-хелпер (`unauthorizedIfNotAllowed`) читает из запроса ТОЛЬКО `headers` — объекта-
  утки достаточно; при незаданном `LOCAL_API_TOKEN` проверка пропускается и в тесте.
- Синглтоны (`mcpClient`, `toolRegistry`) подменяй методами на время прогона и обязательно
  возвращай в `finally` — иначе следующий сьют в цепочке получит твои стабы:
  `const saved = mcpClient.callTool; mcpClient.callTool = …; try { … } finally { mcpClient.callTool = saved; }`
  (тот же приём, что в `orchestrator_cycle_test.mjs`).
- `next/server` и алиасы `@/` импортируются и под `bun`, и под `tsx` — отдельный
  фреймворк (vitest/jest) для api-смоков не нужен.
- **Гейт вида «роут не зовёт LLM» собирается из двух половин, каждая слепа по отдельности:**
  1) контракт исходника: в файле роута нет `createLLM` / `executePipelineRun` / `streamText` /
  `LLM_MODEL` / `LLM_BASE_URL`; 2) поведенческий вызов на моке: точные аргументы,
  ушедшие в `callTool`, и честные статусы (400 битый payload, 503 нет соединения —
  причём `callTool` при 503 НЕ вызван, 500 с реальным текстом исключения).
- Сегмент-проверки хуков делай срезом между объявлениями, а не по всему файлу:
  `runHook.slice(runHook.indexOf('const directTestTool'), runHook.indexOf('const approveTool'))` —
  иначе поисковая строка находит старый код в другом месте и тест врёт зелёным.

## Стаб внешнего сервиса обязан быть согласован с НАСТОЯЩИМ валидатором

Провайдерская цепочка (orchestrator → validator → change_tracker) в смоке исполняется по-
настоящему: стабишь только `mcpClient.callTool`, а валидатор сверяет ответы стаба между
собой. Падает гейт со статусом шага `failed`, `validationRule` пустым и `toolCallExecution`
содержащим успех — валидатор отверг СТАБ, не код:

- **Печатай `step.validationResult.issues`, а не статус.** Текст валидатора прямо называет
  причину: «Element 1001 was not found among the recent model changes» (id из ответа create
  не совпал с elementId в ответе change_tracker), «tool response carried no element id»
  (ответ delete без id, который валидатор обязан верифицировать), «Пустой data» (тул
  попросту забыли включить в стаб и он ушёл в дефолтную ветку).
- **Единый id через ВСЕ ответы одного сценария:** `createdElementId` в create, `elementId`
  в записи change_tracker и ожидаемый changeType (ElementsAdded vs ElementsDeleted) —
  три места, которые обязаны говорить об одном элементе; ответ delete/modify тоже должен
  нести element id.
- **Изолируй сценарий в минимальном репро, прежде чем править код:** тот же шаг через
  прямой вызов `executePipelineRun` (без пауз/групп/resume) на чистом стабе. Проходит в
  изоляции и падает в тесте = дефект стаба или порядка сценариев; падает и в изоляции =
  настоящий дефект кода. Этот сплит решает за минуты то, что иначе уходит в поиск по
  валидатору.
- Счётчики (`log.length`) в id ответов — ловушка: id должен быть фиксированным или
  согласованным со стабом change_tracker, а не зависеть от порядка вызовов.

## Логика React-хука без React и DOM

Выноси тело обработчика в чистую функцию с инжектируемым портом состояния — референс:
`runTurn(args, io, svc)` в `hooks/useAgentRun.ts`.

- `args` — снимок состояния на момент вызова (как замыкание рендера); `io` — набор
  однострочных лямбд поверх `setState` (в тесте — In-memory store с журналом вызовов);
  `svc` — инжектируемые сервисы (`runAgentRequest`, headers, история) — в тесте шпионы/fake.
- Смок гоняет РЕАЛЬНЫЙ флоу: порядок вызовов `setState` (журнал фиксирует последовательность),
  все схемы дедупа, AbortError-ветка, resume-режимы (autoApprove/reject) — без
  рендеринга и без `@testing-library`.
- Хук = объявление состояния + сборка `io`/`svc` + вызов `runTurn`; хук-функция при этом    НЕ тестируется напрямую — тестируется ядро, а хук покрывается контракт-тестом исходника.
- Контракт-тест «в хуках нет мемоизации» проверяй regex'ом именно на **вызовы**
  `useCallback\s*\(` / `useMemo\s*\(` — упоминание запрета в комментарии кода иначе
  фальшит падение, и гейт красный без единого дефекта.
- **Падения счётчиков ожиданий — тоже дефект теста, а не кода:** проверка «первая строка
  DESC — run-X» после UPSERT того же run_id с бо́льшим ts и проверка записи, которой нет
  в `LIMIT`, падают на неверном ожидании. Сверяй ожидание с реальной сортировкой/лимитом,
  а не с порядком вставки.
