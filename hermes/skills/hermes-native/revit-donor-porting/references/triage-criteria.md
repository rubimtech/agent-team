# Критерии триажа донорского кода

Фиксированные критерии вердикта. Заполняются по каждому проекту, не «по ощущению».

## 1. Суть

1–3 предложения: что инструмент реально делает. Формулировка через результат
(«раскладывает площадь пола по помещениям»), а не через механизм донора
(`MainWindow.Button_Click`). Если суть не формулируется — код не прочитан.

## 2. Дублирование

Проверяется по смыслу против своего индекса тулов, а не по имени:

| Шаг | Как |
|---|---|
| Имена тулов | из атрибутов `[McpTool(Name=…)]` в коде, не из документации |
| Поиск домена | по подстрокам: `rebar`, `steel`, `room`, `sheet`, `view`, `dimension`, `material`, `pattern`, `link`, `phase`, `workset`, `export` |
| Сверка | открыть `InputSchema` совпавшего тула: если его аргументы покрывают задачу — это ступень 1 лестницы, «расшинить аргумент», а не новый инструмент |
| Модули | `Modules/*` — сервисы без `[McpTool]` считаются незакрытым спросом |

Вердикт дублирования: `нет` / `частично (что именно не покрыто)` / `да`.

## 3. Портабельность 0–5

| Балл | Значение |
|---|---|
| 5 | чистая геометрия/параметры, переносится почти 1:1 |
| 4 | малая адаптация (переименование, другая точка входа) |
| 3 | переносимо, но требует переработки части логики |
| 2 | глубокая привязка к UI-диалогам или к последовательности ручных шагов |
| 1 | почти не переносимо без переписывания |
| 0 | не переносимо (только UI, или только интеграция с чужим облаком) |

## 4. Блокеры — проверять по коду, не по `.csproj`

| Блокер | Почему мешает именно нам |
|---|---|
| `IExternalEventHandler`, своя очередь, `ExternalEvent` | тело MCP-тула уже выполняется на потоке Revit (ADR-007) — своя очередь лишняя и вредна |
| `static`-синглтоны, глобальный `static Document` | ломает DI, мультиверсионность и параллельные вызовы; заменяется конструкторной инъекцией |
| ClosedXML / EPPlus / NPOI | не «плюс», а помеха: слой работы с таблицами уже есть свой, алгоритм должен выражаться через него |
| `System.Drawing` / GDI, скриншоты | в MCP-туле нет окна для захвата; визуальная проверка — отдельный слой, не ядро инструмента |
| Логика в UI-слое, `System.Windows` вне ViewModel | по правилам MVVM и разделению слоёв это не переносится вовсе |
| `#if REVITxxxx` в бизнес-коде | у нас различия версий только в `Modules/VersionCompat/` |
| Метаданные лицензирования (файл-коннектор к облаку) | выбрасывается целиком, логики не несёт |

## 5. UI-потребность

Хватает ли параметров `inputSchema` + структурированного ответа. Один инструмент или
набор из нескольких — определяется числом независимых входов и результатов.
Визуальный выбор (пипетка цвета, выбор элемента мышью) → либо явный параметр, либо отказ.

## 6. Приоритет 0–100

Упорядочивает очередь; решение к пользователю — из вердикта, не из числа.

```
priority = value(0..5) × portability(0..5) × 10 − duplication_penalty(0..50)
```

- `value` — ценность для инженера-проектировщика (проектирование, документация, ОВК/ГВС)
- `duplication_penalty` — 50 при полном дублировании, 25 при частичном, 0 при отсутствии

## 7. Вердикт

`портировать` / `портировать позже` / `проигнорировать` + одна фраза почему.
Формулировка причины обязательна: без неё рейтинг нельзя пересмотреть, когда
через месяц поменяется приоритет.

## Формат вывода

Три корзины, в каждой — строка на проект:

```
ПОРТИРОВАТЬ (N)
- <project> — <суть одной строкой> · <приоритет> · <1–3 новых инструментов>

ПОЗЖЕ (N)
- <project> — <почему не сейчас>

ИГНОРИРОВАТЬ (N)
- <project> — <причина>
```
