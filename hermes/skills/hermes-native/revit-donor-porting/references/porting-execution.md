# От рейтинга к исполнимому плану

Детализация этапа 2 из SKILL.md: как проверить инфраструктурные допущения до того,
как заложить их в план, и что обязательно зафиксировать в самом плане.

## Проверка цепочки регистрации тулов

Прежде чем планировать ручную регистрацию нового инструмента, пройди цепочку и
запиши в план вывод. Типовой путь (проверяй в своём репозитории по именам):

1. Точка входа хоста после регистрации тулов хост-сборки: какие сборки передаются
   в реестр сверх `Assembly.GetExecutingAssembly()`.
2. Прелоадер модулей: грузит ли он DLL по манифесту (`*.module.json`) и в каком
   режиме сканирования (`TopDirectoryOnly` пропустит вложенную папку `Modules/`).
3. Реестр: есть ли `RegisterAssembly` со сканом `[McpToolAttribute]`.
4. Модуль уже имеет `module.json`? Если нет — это первая правка плана, а не последняя.

Вывод формулируется прямо: «достаточно создать `Modules/<X>/Tools/*.cs`; правки
`Host.cs`, реестра, csproj и манифеста не нужны». Иначе агент будет переделывать
регистрацию, которой и так нет.

Эталон паттерна ищи в уже обёрнутом модуле того же репозитория: namespace
`<Module>.Tools`, наследование `McpToolBase`, атрибут `[McpTool(Name=…, Description=…)]`,
`InputSchema` через сериализацию объекта в `JsonElement`.

## Проверка SDK-globbing перед параллельной работой

```bash
grep -nE 'Compile (Include|Remove)' <проект>.csproj
```

Нет явных `<Compile Include>` для каталога тулов → стиль SDK, новые `.cs` подхватываются
сами. Тогда параллельные агенты не конфликтуют на csproj, и правило распределения
упрощается до «один агент = один новый файл». Обнаружишь явные `Compile Include` —
учти, что каждый агент будет драться за один и тот же список файлов.

## Подключение отсутствующей сборки Revit API

Порядок, который снимает обе рискованные догадки:

1. Найти в пакетном менеджере (`Directory.Packages.props` или `packages.config`)
   переменные версий Revit API. Запомнить **как запинены** существующие пакеты.
2. Проверить наличие пакета и нужных версий в реестре пакетов. Версии нового пакета
   должны совпадать с запинненными у уже подключённых пакетов того же года.
3. Проверить в локальном кэше пакетов, есть ли нужная версия. Нет → потребуется
   один restore из сети; это не блокер, но об этом надо сказать владельцу явно.
4. Проверить тип пакета: `ref/<tfm>/` без `lib/` означает reference-only — DLL не
   копируется в выгрузку, а используется только для компиляции. Проверь, что `<tfm>`
   пакета совпадает с `TargetFramework` конфигурации (в проектах с несколькими
   версиями Revit это могут быть `net48`, `net8.0-windows…`, `net10.0-windows…`).
5. Найти список исключений сборщика (обычно `ilrepack-exclude.txt` или аналог) и
   убедиться, что соседние API-сборки там уже есть.
6. Записать в план готовый diff: `PackageVersion` с тем же условием, что и у соседей;
   `PackageReference`; строка исключения; необходимость обновить и закоммитить
   lock-файл, если он есть в репозитории.
7. Обязательные команды проверки — **крайние версии, а не только текущая**: самая
   ранняя и самая поздняя (у них самые необычные `tfm`). Плюс проверка выгрузки:
   DLL из reference-only пакета не должна ни смержиться, ни задвоиться.

Комментарий в плане обязателен там, где в файле есть предупреждение о сетевом
restore: без пояснения следующий агент «упростит» условие до плавающей версии.

## Проверка донорского движка перед решением «обернуть»

Скан по каталогам сервисов и хелперов (не по всему проекту) на:

| Маркер | Вывод при > 0 |
|---|---|
| обвязка донора, собственные UI-сервисы | логика сплетена с чужим UI — нужен разбор, а не обёртка |
| `static Document` / `static UIApplication` | ломает DI: заменяется инъекцией |
| `IExternalEventHandler` / `ExternalEvent` | лишнее: тело тула уже на потоке Revit |
| `System.Windows`, диалоги, пипетка цвета | 1–2 файла — заглушка + `McpResult.Error` |
| MVVM-типы (`ICommand`, `ObservableCollection`) | редакторное состояние, в MCP не переносится |

Количество чистых строк в `Services/`+`Helpers/` против `ViewModels/` — главный
аргумент в решении «обёртка вместо порта». Приводи числа в плане: они снимают спор.

Отдельно проверь ручную композицию (`*Composition.cs`, `*Container.cs`): если
зависимости собираются в конструкторе без Service Locator, обёртка сводится к
фасаду. И проверь видимость сервисов — `internal` требует фасада, `public` позволяет
вызывать напрямую.

## Что обязано быть в плане

- Решение владельца по каждому блокеру, с датой и обоснованием — чтобы следующая
  сессия не переоткрывала вопрос.
- Готовый diff для точечных правок, а не описание словами.
- Команды сборки по конфигурациям, которые обязаны пройти.
- Раскладка по агентам: ветка, файлы, что делает, порядок инструментов внутри.
- Явное указание, какие проекты **разблокированы** решением, и стартовать после него.
- Раздел «с чего начать в чистом контексте»: нумерированные шаги + правило, что план
  — единственный источник истины по решениям, а рейтинг не пересказывается по памяти.
- Что осталось непроверенным. План, который выглядит завершённым, но не проверен
  сборкой, вреднее открытого списка — он снимает вопрос, не закрывая задачу.
