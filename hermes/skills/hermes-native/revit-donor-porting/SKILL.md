# Портирование алгоритмов чужих Revit-плагинов в наш MCP-каталог

Отбор и перенос алгоритмов сторонних Revit-плагинов (декомпилированных или с исходниками)
в RevitAiTools: что портировать, что пропустить, и как портировать без нарушения контрактов.
Репозиторные правила порта живут в `docs/ADDING_FUNCTIONALITY.md` («Портирование чужого кода»)
и `docs/MARKI_ARCHITECTURE_ADHERENCE.md`; этот навык — **отбор**, который решает, что
вообще портировать, и не даёт начать перенос не с того конца.

Смежное: `revit-reuse-ladder` (дисциплина переиспользования перед новым символом),
`revit-mcp-tool-operations` (работа с каталогом тулов в рантайме).

## Порядок работы

1. **Инвентаризация донора — одним проходом, скриптом.** Донор лежит версиями
   (`<Project>/<Project>_2019 … _2026`), поэтому `find | wc` в цикле по каталогам
   упирается в таймаут. Один обход `os.walk` с подсчётом строк на проект и на последнюю
   версию; промежуточные версии нужны только чтобы понять, дрейфует ли код.
2. **Разделить алгоритм и UI по ПАПКАМ, а не по имени файла.** Классифицируй по имени
   директории (`View`, `Views`, `ViewModels`, `Controls`, `Properties`) — не по регулярке
   по имени файла. Причина: у вложенных проектов логика лежит в `Models/`, `Services/`,
   `Contexts/`, а не в корне, и файловая эвристика объявляет `%alg = 0` у проекта с
   17k строк реального кода. Проверяй выборочно топ-10 файлов по размеру в «алгоритмических»
   папках, прежде чем доверять проценту.
3. **Сгенерировать свой индекс тулов и проверить дублирование ДО любых выводов.**
   Имена — из атрибутов `[McpTool(Name=…)]` в коде, не из документации (гайд отстаёт).
   Буквальное совпадение имён — не дублирование: сверяйся по смыслу (домен, глагол),
   ищи по подстрокам домена (`rebar`, `room`, `sheet`, `dimension`, `pattern`).
4. **Проверить `Modules/*` на неэкспонированные движки.** Модуль без единого `[McpTool]`
   — это готовая реализация, которую никто не обернул в MCP. Донорский аналог такого
   движка тогда не портируется, а оборачивается существующий (лестница переиспользования,
   ступень 2). Считать тулы мало: считай и сервисы в `Modules/`.
5. **Вердикт по каждому проекту** — по фиксированным критериям (см. ниже и
   `references/triage-criteria.md`): суть, дубли, портабельность 0–5, блокеры,
   UI-потребность, приоритет 0–100, решение.
6. **Выдать рейтинг тремя корзинами**: портировать сейчас / портировать позже /
   проигнорировать, с одной строкой причины на проект. Список из 80+ пунктов без
   корзин бесполезен — решение должен принять человек за один проход.

Шаги 1–6 дают рейтинг. Если владелец просит реализацию (а он почти всегда просит —
рейтинг без плана не выполняется), продолжай по этапу 2.

## Этап 2: от рейтинга к исполнимому плану

Рейтинг — вход. Дальше нужны решения, которые рейтинг не закрывает, и раскладка
работы на непересекающиеся куски. Порядок:

1. **Закрыть блокеры решениями владельца, а не списком вопросов.** Два блокера,
   которые обычно всплывают, решаются выбором, а не исследованием:
   - **не подключённая сборка Revit API** (например IFC-экспортёр) — сверить версии
     пакета и записать готовую инструкцию подключения, см. `references/porting-execution.md`;
   - **существующий движок без MCP-обёртки** — обёртка почти всегда дешевле донора.
   Сформулируй варианты с ценой каждого и попроси решение одним раундом; не жди
   ответа, оставляя зависимость висеть.
2. **Проверить, как новые тулы попадают в реестр.** Часто оказывается, что
   `Host.cs`, реестр, csproj и манифест трогать не надо — модуль уже грузится
   прелоадером, а `[McpTool]` сканируется рефлексией. Проверь цепочку до того, как
   закладывать в план ручную регистрацию.
3. **Разложить по параллельным независимым кускам.** Проверь, что csproj
   использует SDK-style globbing: тогда новые `.cs` подхватываются сами и правки
   csproj не конфликтуют между агентами. Правило — один агент = один новый файл;
   общий файл (`Directory.Packages.props`, csproj, реестр) достаётся ровно одному агенту.
4. **Задать порядок внутри куска.** Начинать с read-only инструмента: он ничего не
   ломает и даёт разбор входа для остальных инструментов того же домена.
5. **Положить в план раздел «с чего начать в чистом контексте».** План читает агент
   без истории сессии: нужен явный первый шаг, и план должен быть единственным
   источником истины по принятым решениям.

Полезные мелочи, которые обязаны попасть в план, иначе их придётся выяснять заново:
готовый diff для точечных правок, команды сборки по конфигурациям, которые обязаны
проверить (крайние версии, а не только текущую), и явная отметка, какие проекты
разблокированы решением владельца.

## Что делать с чужим кодом

- **Алгоритмы, не файлы.** Каждый `.cs` переписывается в стиле репозитория; таблица
  обязательных замен — в `docs/ADDING_FUNCTIONALITY.md`.
- **UI донора не портируется.** WPF/MVVM и code-behind выбрасываются; параметры
  переносятся в `inputSchema`. Визуально-зависимое (пипетка цвета в окне, выбор
  элемента мышью) либо выражается явным параметром (например, hex цвета), либо проект
  выбрасывается.
- **Метаданные лицензирования — не логика.** Файл регистратора плагина от поставщика
  обычно реализует только интерфейс (имя, цена, классы команд) — это выбрасывается
  целиком и не влияет на портабельность.
- **«Поддержка R22–R27» у донора часто фиктивна.** Сравни строки последних версий: если
  R25 и R26 совпадают, это копии под конфигурации, а не реальная мультиверсионность.
  Портируй против API R26 и прячь различия в `Modules/VersionCompat/` — не переноси
  `#if REVITxxxx` из донора.

## Проверка утверждений о Revit API по метаданным

Донорный код регулярно ссылается на члены и значения `BuiltInParameter`, которых нет
в API — и агент, портирующий его, может это заметить, а может выдумать. Любое
утверждение о несуществующем члене, «устаревшем» имени или числовом коде параметра
проверяется по файлу документации пакета, а не по памяти и не по доверию к отчёту:

```
~/.nuget/packages/<vendor>.<product>.revitapi/<версия>/ref/<tfm>/RevitAPI.xml
```

XML содержит полные имена членов и числовые значения `enum`. Достаточно вычитать его
целиком и искать по имени и по коду. Именно так подтверждаются и исправляются
ошибки донора: несуществующий член `enum`, read-only свойство, перепутанный
`BuiltInParameter`, имя типа, отсутствующее у элемента.

Правило проверки кода агента: **приписывай чужой баг репозиторию, только если сверился
с метаданными.** Расхождение «агент выдумал API» и «агент нашёл баг донора» внешне
выглядит одинаково, а цена ошибки противоположна — либо выкинуть рабочий код, либо
закоммитить несуществующий вызов.

## Ловушки

- **Вердикт по размеру проекта, а не по сути.** 25k строк могут быть 90% UI-обвязки или
  перебором конфигураций. Ранжируй по `alg_lines` и портабельности, не по `lines`.
- **Не выдавай совпадение подстроки за дублирование.** Донорский «трубный» инструмент
  и наш модуль соединения труб — тема одна, API разные; читай оба, потом решай.
- **Не оценивай блокеры по `.csproj`.** Зависимость от Excel-библиотеки — помеха, а не
  факт: проверь, можно ли выразить алгоритм через уже имеющийся слой работы с таблицами.
- **Не обещай «портабельность» без чтения кода.** Приоритет, названный по имени проекта,
  это догадка; прочитай `Models/`+`Services/` и только потом ставь балл.
- **Перед подключением новой сборки Revit API проверь версионную политику репозитория.**
  Поищи в `nuget.config` офлайн-фоллбэк и плавающие версии вида `$(RevitVersion).*`:
  плаващая версия заставляет NuGet перечислять версии по сети, и на машине без
  доступа к nuget.org restore падает `NU1301`, блокируя всю сборку. Новая зависимость
  обязана идти через уже запинненную переменную того же года, а не через новую
  плавающую. Сверь, что нужные версии пакета существуют для всех поддерживаемых
  версий Revit, до того как вносить правки.
- **Проверь, что сборка из SDK-пакета исключена из ILRepack.** Если рядом уже
  исключены `RevitAPI`/`RevitAPIUI` — эти DLL грузит сам Revit из папки установки,
  а пакеты нужны только для компиляции. Новую сборку надо добавить в тот же список
  исключений, иначе сборка пытается смержить её и ломает выгрузку.
- **Не переноси чужой UI-диалог в MCP-тул.** Проверь сервисный слой донорского
  движка сканом на UI-зависимости и перечисли исключения поимённо: если нужные
  99% кода чисты, порт сводится к тонкой обёртке с заглушкой на диалоги, а «диалог
  показывается пользователю» становится `McpResult.Error`. Это меняет вердикт с
  «не портировать» на «обернуть», поэтому проверка обязательна до вынесения вердикта.
- **Не теряй выигрыш от субагентов на бэкаенде субагента.** Транскрипты могут быть
  обрезаны в превью, а сводный отчёт батча — единственное место с полными вердиктами.
  Пересчитай выводы по нему, а не по тому, что успел увидеть в логе, и не выдавай
  первый рейтинг наружу до получения батча: ранний список в этой сессии содержал
  проект, который по факту был лучшим кандидатом волны.

## Проверка

- [ ] Индекс донора построен и сохранён (проекты, версии, `alg_lines`/`ui_lines`)
- [ ] Свой индекс тулов построен из атрибутов, дублирование проверено по смыслу
- [ ] `Modules/*` проверены на неэкспонированные движки
- [ ] У каждого проекта — вердикт по всем критериям, а не только по приоритету
- [ ] Вывод — три корзины, а не один длинный список
- [ ] Ограничения вывода (что не прочитано, что не проверено) названы явно

Если владелец запросил реализацию:

- [ ] Блокеры закрыты решениями владельца, а не остались вопросами
- [ ] Проверена цепочка регистрации тулов (план не предлагает лишние правки)
- [ ] Проверен SDK-globbing: параллельные агенты не будут драться за csproj
- [ ] Общий файл (props/csproj/реестр) достаётся ровно одному агенту
- [ ] В плане есть раздел «с чего начать в чистом контексте»
- [ ] Непроверенные пункты плана названы явно

Подробности этапа 2 — `references/porting-execution.md`; фиксированные критерии
вердикта — `references/triage-criteria.md`.
