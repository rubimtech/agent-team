# Задание с недоступным оркестратором: адаптация и запуск

Рецепт для класса задач: бриф предписывает работу через конкретный инструмент
диспетчеризации (`agent_manager`, `dispatch`, и т.п.), которого в сессии нет.

## Порядок

1. **Убедиться, что инструмента действительно нет.** Проверить каталог отложенных
   инструментов (`tool_search` по названию и по действию), а не только список
   инструментов сессии. Отсутствие в списке — недоказанное отсутствие.

2. **Не останавливать работу.** Бриф с «остановись и доложи» написан под ситуацию,
   где контур неисправен. Здесь контура нет — это другое. Выполнять задачу теми
   же правилами вручную: один писатель, гейты с CHECK/EXPECT, evidence, приёмка
   оркестратором.

3. **Выполнить шаги брифа по существу, а не по букве.** Шаги «проверить
   окружение», «зафиксировать базовую линию», «убрать остатки прошлого пилота»
   полезны независимо от способа диспетчеризации. Пилот заменяется первым же
   реально выполненным гейтом.

4. **Прочитать реестр задач и построить раскладку самому.** Источник истины —
   `docs/agents/task-registry.yaml`: у задачи есть `depends_on`, `owns`,
   `gates`, `status`. Готовые к запуску = `status: pending` со всеми
   зависимостями `verified`.

5. **Запустить независимые задачи параллельными субагентами.** Один субагент = одна
   задача на непересекающемся OWNS. Оркестратор в это время берёт задачи, чей OWNS
   не пересекается ни с чьим, — иначе простаивает половина запуска.

6. **Приёмка по файлам и гейтам, не по отчёту субагента.** Отчёт — самоотчёт.

## Обязательные части брифа субагенту

Без них субагент либо упирается в чужой OWNS, либо выдумывает API.

| Часть | Зачем |
|---|---|
| Список «твои файлы» и «чужие OWNS не трогать» | граница записи |
| Абсолютные пути к канону | не выдумывает, читает первоисточник |
| Точные команды гейтов с ожидаемым кодом возврата | проверяемость |
| Контракт файла из чужого OWNS | если он импортируется — имена импортов |
| Правила проекта (деньги, язык, запреты) | дефект вместо несоответствия |
| Запрет коммита и `git add -A` | коммит у оркестратора |
| Требование привести фактический вывод | не «должно работать» |

## Ошибки брифа, которые надо находить, а не исполнять

Бриф копит канон, и канон копит историю. Проверять перед исполнением:

- **Рекомендация по зависимости.** Проверить, что пакет вообще даёт нужный модуль
  (пробный импорт), а не только что он ставится.
- **Формат значения.** Таблица настроек в документе может перечислять логические
  имена, тогда как весь код и окружение используют префикс. Искать документ с
  примером реализации и всех потребителей (`scripts/`, CI, compose, `.env.example`).
- **Ожидаемое число провалов.** «Ожидается N» — это ориентир, а не истина; сверять
  с фактическим прогоном и объяснять расхождение, а не подгонять.

## Что писать в отчёт

Формат брифа (что сделано / проверка / изменённые файлы / блокеры) сохраняется.
Отдельно указать, что контур диспетчеризации заменён ручным, и перечислить, что
осталось непроверенным. Непроверенное помечать непроверенным: `n/a` без причины —
это провал, замаскированный под успех.
