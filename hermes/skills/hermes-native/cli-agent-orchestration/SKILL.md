# Управление локальными CLI-агентами (Kilo CLI / Claude Code / Orca)

Класс задач: поставить сторонний CLI-агент на реальную работу (правки кода, ревью, сборка, массовые
операции в репозитории), получить изолированный результат и **самому** убедиться, что он верен.
Отличие от `delegate_task`: CLI-агент — отдельный процесс в своём git-worktree, со своими доступами,
своими лимитами и своими деньгами; его отчёт о результате — самоотчёт, а не факт.

## Порядок работы

1. **Искать бинарники на диске, а не в `PATH`.** Инструмент, «не установленный» по `which`/`--version`,
   часто уже лежит внутри расширения IDE или приложения. Проверять по местам установки, а не только в PATH:
   ```bash
   ls -1 "$HOME/.vscode/extensions" | grep -i -E 'claude|kilo|copilot'    # расширения-обёртки CLI
   ls -1 "$LOCALAPPDATA/Programs" "$HOME/AppData/Roaming" 2>/dev/null | grep -i <имя>
   find "$LOCALAPPDATA/Programs/<app>" -maxdepth 3 -name '*.exe' 2>/dev/null   # CLI внутри ресурсов приложения
   ```
   Найденный бинарник вызывать полным путём: полный путь работает всегда, алиасы — только в новой сессии.
2. **Снять интерфейс до того, как строить сценарий:** `<bin> --help` (или `--version`), затем у самого
   приложения — встроенные гайды под установленную версию (`<app> skills list` / `skills get`, `agent-context`,
   `status`). Документация в интернете описывает свежий релиз и расходится с локальной сборкой; источник
   правды — `--help` установленного бинарника. Смотреть на признаки headless-режима (`run`, `serve`, `--print`,
   `--output-format`, `--permission-mode`) — от них зависит, годится агент для автоматизации или только для GUI.
3. **Смоук-тест на скрэтч-репе, прежде чем пускать агента в рабочий репозиторий.** Задача-пустышка
   (создать/прочитать файл, вернуть вывод) в `$TMPDIR`-папке; проверяются: код возврата, наличие вывода,
   персистентность авторизации (второй запуск без логина), поведение при таймауте. Гейт пройден — только
   тогда рабочие репозитории.
4. **Изоляция — git-worktree на каждого агента**, ветка на задачу, `.kilo/worktrees/<name>` (там же, где их
   держит сам инструмент; реестр активных деревьев — `.kilo/agent-manager.json`). Один worktree — один
   агент, один файл — один писатель; иначе агенты молча затирают друг друга и diff перестаёт что-либо значить.
5. **Один драйвер на все агенты.** Скрипт вида `agent-run -Agent claude|kilo|orca -Task <файл> -Worktree <путь>
   -TimeoutSec N` с логом, замером времени и кодом возврата: разные CLI-агенты имеют разные флаги, и без
   общей обёртки каждый запуск превращается в набор заново придуманных команд. Таймаут обязателен —
   автономный агент умеет висеть бесконечно.
6. **Проверка результата — внешняя.** `git diff` в дереве, наличие файлов, повторное чтение изменённого
   фрагмента, прогон гейта репозитория, exit code. Формулировки «агент сообщил, что сделал» в отчёт не идут.
7. **Стоимость и доступы — за владельцем.** Авторизации, добавление путей в `PATH`, массовые параллельные
   запуски (платные вызовы) согласовывать, а не решать молча.

## Ловушки

- **Не в PATH — не значит «не установлено».** Обратный вывод тоже неверен: `npm -g ls` показывает только
  глобальные пакеты и «прячет» CLI, живущие внутри расширений IDE.
- **Приложение с GUI ≠ работоспособный headless.** У настольного приложения может быть собственный
  рантайм-сервер (`<app> serve`) и собственный способ регистрации управляемых аккаунтов — проверять их
  наличие, а не судить по наличию GUI-окна.
- **Авторизация истекает молча.** Первый запуск проходит, второй спустя сутки — нет, а признак ошибки
  приходит не всегда в exit code. Сохранять логи каждого прогона и не смешивать отказ авторизации с
  провалом задачи.
- **Не пускать флот в рабочий репозиторий до смоук-тестов** и не логировать содержимое окружения
  (токены приходят через переменные) — логи уходят в репозиторий вместе с отчётом.
- **Роль агента, скил и бриф пишутся с ПОЛНЫМИ абсолютными путями** (включая пути к файлам скилов):
  файл должен исполняться агентом целиком, без поиска и доуточнений. Проверять существование каждого
  указанного пути скриптом, а не глазами.
- **Инструмент в брифе может отсутствовать — адаптировать, а не останавливаться.** Если задание называет
  конкретный оркестратор (`agent_manager` и подобные) и его нет в наборе инструментов, работать самому:
  выполнить поток теми же правилами (один писатель, гейты, evidence), а независимые задачи раздать
  параллельным субагентам. Отметить в отчёте, что контур заменён, иначе «пилот не запускался» будет
  выглядеть как отказ от задачи.
- **Ошибка в собственном указании субагенту — исправлять немедленно.** Если бриф или канон разошлись,
  отправлять `steer` с верным вариантом и причиной, пока код не зафиксирован; иначе неверное решение
  входит в коммит и расходится с остальными потребителями.

## Параллельные субагенты: OWNS вместо числа

Раскладку «сколько задач в раунде» задаёт граф, а не желание ускориться. Перед запуском
проверить, что OWNS задач попарно не пересекаются (префикс пути внутри другого — тоже пересечение).

- Каждому субагенту в брифе передаётся явный список «твои файлы» и «чужие OWNS не трогать».
- Субагенту, чья задача опирается на файл из другого потока, даётся контракт этого файла (точные
  имена импортов), а не только описание намерения: он не видит соседнюю работу.
- Приёмка — по файлам и гейтам, а не по сообщению субагента о завершении.

## Ловушка: «n/a» выглядит как успех

Проверочные скрипты помечают шаг `n/a` с причиной, когда нет инструмента, переменной или тестов.
Итоговая таблица от этого может показать ноль провалов там, где раньше были красные шаги.

- Сравнивать по базовой линии все четыре счётчика: выполнено / пропущено / прошло / провалено.
  Упавший «провалено» при выросшем «пропущено» — это регрессия, а не победа.
- Каждый `n/a` обязан называть причину. `n/a` без причины = непроверенный гейт, считать провалом.
- Перед выводом «инструмент не установлен» прочитать сохранённый пользовательский PATH и подставить
  его в сессию: `Get-Command uv` может вернуть пусто при установленном `uv` в `~/.local/bin`, и тогда
  каждый шаг, которому он нужен, молча станет `n/a`, а сводка покажет зелень.
- После исправления окружения прогнать проверку целиком: настоящее число провалов после починки
  часто хуже ложной зелени, которую оно заменило.

## Канон важнее брифа

Если задание, план или собственная догадка противоречат коду — выигрывает канон реализации. Найти
документ с фактической формой (пример класса, пример env, существующий импорт) и совпасть с ним:
префиксы переменных, имена функций, модулей и полей — это контракты, которые читают compose, CI,
проверочные скрипты и уже написанные вызовы.

- Перед решением грепнуть всех потребителей значения по `scripts/`, CI-конфигам и документу с кодом.
- Противоречие двух канонических документов само по себе находка: записать его в evidence, чтобы
  следующая сессия не выясняла заново.
- Плагин или расширение из конфига сначала доказать импортом: пакет с одними `.pyi`-стабами
  удовлетворяет «установлен», но импорт, который нужен инструменту, падает, и инструмент сообщает
  об этом как об ошибке загрузки плагина, а не об отсутствии зависимости.

## Живость субагента: артефакты, а не время

Диспетчер сообщает статус, а не прогресс. Субагент, который «работает» и субагент,
который завис, неразличимы по статусу — различимы только по дереву репозитория.

| Признак | Вывод |
|---|---|
| Файлы меняются, растёт число тестов или строк | Живой — дать работать |
| Артефакты не меняются несколько проверок | Подозрительно |
| Высокий возраст И нет артефактов И steer без ответа | Зомби — остановить |
| Артефакты движутся медленно, но монотонно | Живой, терпение |

Возраст сам по себе ничего не доказывает: ребёнок, у которого число тестов растёт
116 → 187 → 294, здоров сколько угодно долго. Для остановки нужны два независимых
сигнала одновременно (нет артефактов + нет ответа на steer), иначе остановка
погасит самую долгую, но самую ценную работу.

- **Замерять дерево самому:** `delegate_task(action='list')` даёт статус; прогресс
  видно по mtime файлов, числу тестов, созданным миграциям, хвосту лога. Ребёнок,
  у которого ничего нет, завис на первом шаге — обычно на документе, который не
  смог разобрать.
- **Steer нести проверенными фактами.** Каждый круг, который ребёнок тратит на
  переоткрытие окружения, — это круг, не потраченный на реализацию. Проверить
  самому и передать: точную падающую команду с дословными строками ошибки
  (включая `file:line`), зелёный базис (полный набор команд, который сейчас
  проходит), порты и readiness-проверку нужных сервисов, данные, которые нельзя
  сносить, и уже принятые решения, иначе они вернутся вопросом.
- **Требовать вывод команд, а не отчёт.** Просьба «исправь ошибки» гарантирует
  ещё один круг: без `file:line` ребёнок ищет то же самое.
- **Ложная тревога на зомби — тоже ошибка.** Ребёнок может читать канон и сверять
  состояние, и это выглядит как отсутствие прогресса. Прежде чем останавливать,
  прочитать лог: работа на согласовании видна по формулировкам.

## Отмена батча — не отмена работы

Фоновый батч присылает уведомление об отмене, когда ребёнок замолчал за порогом
без прогресса. Всё, что он успел записать, уже лежит на диске и часто закончено и
годно.

1. Прочитать дерево и прогнать гейты **до** любого вывода.
2. Если работа проходит гейты — принять её, а не передиспетчеризовать.
3. Передиспетчеризовать только недостающую часть.

Повторный запуск уже упавшей работы дублирует файлы, съедает контекстное окно и
оставляет две расходящиеся версии одного модуля, которые гоняются между собой.

## Приёмка: зелёное — не значит подключённое

Субагент может сдать файл, который проходит `ruff`, `mypy` и `tsc`, но нигде не
импортируется. Статические проверки доказывают, что код компилируется; слово
«работает» они не доказывают.

| Артефакт | Доказательство связности |
|---|---|
| Новый модуль | Присутствует в графе импортов точки входа |
| Новый роут или страница | Строка роута видна в собранном бандле |
| Новая зависимость | Имя пакета найдено в выводе сборки |
| Новый эндпоинт | Путь присутствует в сгенерированной спецификации |
| Новый ключ конфигурации | Путь чтения прогнан тестом |

Зелёная сборка плюс неимпортированный файл — тихий no-op, хуже громкого падения,
потому что переживает ревью. Соблазн «подключить сейчас» надо сверять с OWNS:
если файл входа принадлежит другому потоку, честнее оставить `gates-pending` с
причиной, чем переписать чужой OWNS ради зелёного статуса.

## Порядок запуска: миграции, потом сид, потом сервис

Идемпотентный шаг (seed, sync, backfill), выполненный слишком рано, не падает —
он молча ничего не делает. Ошибки нет, поэтому и не видно.

- Порядок объявлять явно: `upgrade` → `seed` → `serve`.
- У идемпотентного шага проверять **результат**, а не код выхода («4 роли, права
  9/5/2/1» вместо «seed ok»).
- Сервис, который поднялся с неверными данными авторизации, — это дефект
  безопасности, который не поймает ни один смоук-тест: логин работает, права нет.

## Проверка

- [ ] Бинарники найдены, интерфейс снят, смоук-тест пройден до рабочих репозиториев
- [ ] OWNS субагентов попарно не пересекаются
- [ ] Зомби остановлены по двум сигналам, не по возрасту
- [ ] Отменённый батч — дерево прочитано, гейты прогнаны, вывод сделан
- [ ] Сданный артефакт доказанно подключён, а не только компилируется
- [ ] Идемпотентные шаги проверены по результату, порядок запуска зафиксирован
- [ ] Порты занятые пользователем не тронуты, переопределение отражено в отчёте
