# Модель как стенд для прогона MCP-инструментов

Рецепт: из строительства модели получить воспроизводимый прогон каталога инструментов с доказательствами.
Годится и для проверки плагина, и для учебных материалов.

## 1. Состав модели

Собирать так, чтобы каждое семейство инструментов имело на чём работать: уровни + сетки (оси), стены разных
типов, перекрытия, двери/окна, помещения, спецификации, листы, параметрическое семейство с типоразмерами и
формулами, группа, Design Options. Плюс целевые показатели объёма (например, большая версия на десятки тысяч
элементов) — для проверок производительности и пакетных операций.

Строить **тем же каталогом**, который проверяешь (discovery-лестница → вызов), а не скриптом сбоку:
иначе тестируется скрипт, а не инструменты.

## 2. Намеренные дефекты

Модель-полигон полезна не «правильностью», а воспроизводимыми ошибками: элементы без марок, дубли марок,
незамкнутые помещения, «мусорные» виды, лист без рамки, элемент нулевой длины, предупреждения Revit. Это
материал для уроков/проверок, которые учат находить и исправлять такие дефекты. Оформляй их списком с
точным составом (сколько чего), а не «есть ошибки».

## 3. Idempotent builder

Один и тот же скрипт/последовательность вызовов, запущенные дважды на чистом файле, дают одинаковый
результат: одинаковые имена, номера, количество элементов. Проверяется повторным прогоном и сверкой
счётчиков — без этого любой дефект далее неотличим от шума.

## 4. Журнал прогона

`tool_runs.jsonl`, одна строка на вызов: `tool`, `category`, `tier`, `status`, `args_sha1`, `latency_ms`,
`readback` (что подтвердило запись). Плюс агрегаты: покрытие по областям (≥1 чтение и ≥1 запись на
область), доля успешных, распределение ошибок по `status`.

## 5. Обязательные негативные проверки

Неверный id элемента, пустой список, запись в несуществующий тип, удаление с `dryRun` и без,
вызов `broken`/`deprecated`, превышение лимита времени на длинной операции. Без них покрытие
одностороннее: «счастливый путь» проходит у любого каталога.

## 6. Формат отчёта о дефекте

Минимальное воспроизведение (последовательность вызовов), ожидание, факт, сырой ответ инструмента,
версия Revit, версия плагина. Без этого отчёт не годится как issue в репозиторий инструментов.

## 7. Гейты приёмки

P1 состав модели соответствует спецификации · P2 builder идемпотентен · P3 покрытие доменов · P4 read-back
после каждого write · P5 негативные проверки пройдены · P6 дефекты оформлены по формату выше · P7 прогон
минимум на двух версиях Revit · P8 каждый пробел каталога (там, где понадобился CSX) записан отдельно.

## 8. Порядок работы

1. Убедиться, что сервер отвечает (Revit запущен, порт из `%TEMP%\revit-mcp-{pid}.json`).
2. Прогнать discovery по всем нужным областям и зафиксировать срез каталога (он же — база сравнения при
   следующем прогоне).
3. Собрать модель, ведя журнал, и проверить её чтением (счётчики, список помещений, спецификации).
4. Прогнать негативные проверки.
5. Оформить дефекты и пробелы каталога; собрать агрегаты из журнала, а не по памяти.
