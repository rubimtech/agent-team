# Проверочный вид в модели пользователя + диагностика границ помещений

Задача класса: «создай вид, чтобы я мог кликнуть и посмотреть, как расположены границы
помещений». Это уже **write** в чужую модель, но пользователь сам его попросил —
значит пишем только то, что нужно для осмотра (вид, кадрирование, марки), и **не
трогаем** геометрию и параметры помещений без отдельной команды.

## Порядок: вид → детализация → кадрирование → марки → проверка

1. `create_plan_view` `{"levelId": <id>, "viewName": "..."}` → возвращает `viewId`.
   Имя делай говорящим и помечай назначение («проверка границ»), иначе вид останется
   в проекте навсегда без понятного назначения.
2. Read-back `get_view_info` — проверить `viewType: FloorPlan`. Потом
   `set_view_detail_level` `{"detailLevel":"fine"}` и `set_view_display_mode`
   `{"displayMode":"flat"}` (для плана читаемее, чем `hidden`).
3. Кадрирование под габариты нужных элементов: собрать `get_room_bounding_box` по
   нужным комнатам, взять объединение min/max и задать рамку.
   - `set_view_crop_box` рамку записывает, но **на кадрирование выдачи не влияет**:
     экспорт всё равно рисует всю модель, потому что камера осталась прежней.
   - Поэтому после рамки обязательно `navigate_view` `{"action":"zoom_to_fit"}` —
     именно это реально переводит камеру, и только после него картинка кадрирована.
4. `batch_tag_rooms` `{"viewId": <id>}` — разом ставит марки всем помещениям вида,
   возвращает `taggedCount` и `tagIds`. Читаемость резко растёт: пользователь видит
   площадь прямо на плане и может сравнить с цифрой из `get_rooms`.
5. Финальная проверка — экспорт картинки и `vision_analyze` (см. ниже про outputPath),
   затем сообщить пользователю `viewId` и что вид уже активен (`set_active_view`).

## Ловушки API, проверенные на деле

- У `ViewPlan` в этой сборке **нет** членов `SetOrientation`, `ShowRoomBoundaries`,
  `ShowOutline`, `CategoryManager` — CSX с ними не компилируется
  (`CS1061`/`CS1955`). Не трать попытки: `ViewOrientation3D` там не конструктор.
- `view.CropBox = bb` через CSX работает (обернуть в `Transaction`), но камеру
  не двигает — см. пункт 3.
- `BuiltInCategory.OST_RoomBoundaries` не существует в этой привязке; включать
  границы помещений надо инструментом `set_view_category_visibility`
  с `categoryId: -2000161`, `hidden: false`.
- `capture_view` работает **только на 3D-видах** (`error: -32603 "Active view is not
  a 3D view"`). Для плана — только `export_view_image`.
- `export_view_image` кладёт файл в CWD как `"<viewName> - <viewType> - <viewName>.png"`;
  путь из `filePath` (папка захватов в `%TEMP%`) может не существовать, а
  `fileSize` всегда 0 — проверяй листингом, не полем ответа.
- `PrintWindow`-захват (`scripts/printwindow_capture.py` навыка
  `windows-uia-automation`) принимает **hwnd, а не PID**: с PID он падает с
  `GetWindowRect failed`.

## Диагностика границ помещений по цифрам

Сверяй `get_rooms.area` с площадью bbox из `get_room_bounding_box`
(дюймы: футы × 0,3048). Расхождение в разы при невеликом bbox означает, что периметр
помещения «натянут» через соседние комнаты, а не по их стенам.

`get_room_info` даёт `boundaryCount` на комнату: единица означает ровно один
замкнутый периметр — сам по себе факт не дефект, но в паре с завышенной площадью
он и указывает на проблему.

Порядок исправления (предлагать пользователю, не применять молча):

1. Проверить у стен параметр **«Граница помещения» (Room Bounding)** — снятый флаг
   уводит контур на середину стены или рвёт его.
2. Проверить, что разделяющие стены реально соединены (джойны), а не стоят рядом:
   Revit сшивает несмежные стены в один периметр насквозь.
3. Открытые площадки (терраса, крыльцо, тамбур) без стен не имеют границ вообще —
   для них нужны **линии разделения помещений** (`create_room_separation_line`) вдоль
   краёв либо граница участка.
4. Задать высоту помещения — без неё объём 0 и площадь годится только для планировки.

После правок обязателен read-back: `get_rooms` снова и те же `get_room_bounding_box` —
числа должны сойтись, и только это даёт право написать «границы закрыты».
