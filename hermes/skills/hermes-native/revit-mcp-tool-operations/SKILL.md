# Работа с Revit через MCP-инструменты RevitAiTools

Репозиторий инструментов — `D:\DEV\RevitAiTools`: плагин `ReVibe`, MCP-сервер и каталог инструментов
(`revitCopilot/`, `revitCopilot/McpServer/Tools/`, ~1100+ инструментов). Источник истины по API —
`docs/MCP_AGENT_GUIDE.md` и `docs/MCP_TOOL_ADD.md`; читай нужный раздел гайда **перед** первым вызовом
семейства. Плагин развёрнут в `%APPDATA%\Autodesk\Revit\Addins\` (проверено: манифест `ReVibe.addin` для
R2022–R2027) — тестировать можно только на развёрнутых версиях, а не на любых установленных.

## Порядок работы (имена инструментов не хардкодить никогда)

1. **Убедиться, что сервер жив — прямым HTTP, а не по наличию в своём списке инструментов.** Revit запущен +
   плагин загружен; порт — динамический (диапазон 18765–18864, `McpPortManager`). Файл порта —
   `%LOCALAPPDATA%\RevitAiTools\mcp\revit-mcp-{pid}.json`, поля **camelCase** (`{"pid":…,"port":…,"name":…}`).
   **Не ищи его в `%TEMP%`:** внутри Revit (хост .NET Framework) `GetTempPath()` возвращает
   сессионный GUID-каталог вида `%TEMP%\b74d7ea4-…\`, а у внешнего процесса — пользовательский
   `%TEMP%`; пути не совпадают и внешний читатель ничего не находит. Канонический каталог под
   LOCALAPPDATA одинаков для обеих сторон, и регистр свойств тоже важен — старый writer писал
   PascalCase, а `System.Text.Json` ищет свойства регистрозависимо, и инстанс не распознавался.
   Файл — признак «сервер запускался», а не «сервер жив»: pid из файла проверяй на живость,
   иначе получишь файлы от мёртвых процессов и решишь, что сервер есть. Рабочий способ: `netstat -ano | grep LISTENING` в
   диапазоне портов, затем `POST http://127.0.0.1:<port>/mcp` c телом `tools/list` — ответ `result.tools`
   подтверждает порт и живость. Эндпоинт именно `/mcp`; `/`, `/sse`, `/messages` отдают `Not found`. Готовый
   клиент — `scripts/mcp_rpc_call.py`, полный безассионный пробник (initialize → tools/list → tools/call) —
   `scripts/probe_mcp.py`. Сервер не отвечает → сначала поднять Revit и плагин, а не угадывать порт и не
   объявлять функцию недоступной.
   4. **Вызов** — ровно с теми аргументами, что в `inputSchema`. Ошибка → читай `status`, `message`,
   `need_input`; не подбирай аргументы наугад и не переписывай вызов «на второй раз».
   - Сервер **безсессионный**: `initialize` может не вернуть заголовок `Mcp-Session-Id`, и `tools/list` /
     `tools/call` работают без него. Отсутствие session id — не признак поломки; не блокируйся на его
     согласовании и не перезапускай handshake в цикл.
   - Тело JSON передавай аргументом curl (`-d '{...}'`) или файлом (`-d @body.json`), **не через stdin**:
     конвейер в сокет не проставляет Content-Length, и HTTPAPI отвечает `411 Length Required` — выглядит
     как «сервер сломан», хотя он жив.
**Stdio-мост одной трубой — когда MCP-инструментов в сессии нет, а порт искать не хочешь.**
Мост `.kilo/scripts/mcp-revit-bridge.cmd` сам выбирает самый свежий Revit с загруженным
плагином и проксирует stdio JSON-RPC на тот же HTTP-эндпоинт, то есть весь разбор конверта
(см. п.3 выше) остаётся в силе. Весь handshake уезжает в одну трубу — initialize,
`notifications/initialized` и `tools/call` обрабатываются последовательно:

```bash
printf '%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"get_selection","arguments":{}}}' \
 | .kilo/scripts/mcp-revit-bridge.cmd
```

Ответы приходят в обрамлении `Content-Length: N` — бери последний JSON-блок. Назначение:
**read-only сверка реальной формы ответа** (какие поля у `get_levels`/`get_parameters`, какой
регистр конверта) ПЕРЕД тем, как писать/чинить клиентский парсер или валидатор, — без
поиска порта, без curl и без единой мутации. Кадр `initialize` в первом же ответе подтверждает
живость и PID инстанса.

2. **Discovery-лестница:** L0 — обзор возможностей и категорий (`get_modeling_capabilities`,
   `capability_get_categories`) → L1 — `capability_search_methods` по «глагол + объект» → L2 —
   `capability_get_method_info` за `inputSchema` и обязательными параметрами → только потом вызов.
   0 результатов → синоним («стена» → Wall/wall_type/create_wall) → и лишь затем CSX. Полный реестр
   доступен мета-инструментами (список/поиск/описание), но не перебирай 1100 имён из памяти: имена
   дрейфуют (`get_walls` ↔ `find_walls`), а часть инструментов имеет `status: broken`.
3. **Формат ответа — конверт проекта, а не MCP `content[]`.** Тулы возвращают
   `McpResponse<T>`: успех — `{"data":{…}}`, ошибка — `{"error":"…","errorCode":"…","details":{…}}`.
   Это попадает в JSON-RPC как `result` целиком, то есть
   `{"jsonrpc":"2.0","id":N,"result":{"data":{…}}}`. Клиент, написанный по спецификации MCP
   (`result.content[0].text`), получит пустой результат и покажет это как «тул мёртв», а на деле
   данные на месте. Клиент обязан понимать обе формы; признак ошибки — `error`/`errorCode`
   на верхнем уровне `result`, а не `isError`.

## Правила вызова (нарушишь — получишь «инструмент не работает»)

- **Единицы разъезжаются:** `create_level` принимает миллиметры, геометрия из `get_*` возвращается в футах,
  а `create_wall.length` — это **толщина**, не длина. Не смешивай в одном расчёте, проверяй фактическое
  значение после вызова.
- **Write-инструменты сами открывают и коммитят транзакцию.** `transaction_commit` вручную не вызывать
  (вешает UI-поток), `transaction_rollback` **не** откатывает уже записанное.
- **Кириллица в аргументах не проходит** — имена типов, параметров и уровней брать из выдачи
  `get_parameters` / категорий, не переводить руками.
- **Всё выполняется в UI-потоке, лимит ~60 с на вызов** — длинную работу резать на порции или уводить
  в CSX с прогрессом и логом.
- **CSX (`code_runner_execute`) запускается ВНЕ транзакции** — в отличие от write-инструментов. Любой
  `Doc.Delete`/`Doc.Regenerate` в скрипте падает с `ModificationOutsideTransactionException`, пока свою
  транзакцию не открыть. Всегда оборачивай в `using (var t = new Transaction(Doc, "..."))`, в длинной
  петле проверяй `t.HasStarted()` — транзакция может закрыться сама, и следующая итерация уронит всё.
- `delete_elements` по умолчанию `dryRun` — сначала посмотреть, что попадёт под удаление, потом `dryRun:false`.
- **Массовое удаление видов/листов — только CSX, три стадии, каждая в своей транзакции.** Ключевое: не
  смешивать листы и виды в одной транзакции (Revit падает `InvalidObjectException`), шаблоны видов удалять
  отдельным проходом, `ProjectBrowser`/`SystemBrowser` удалить нельзя. Полный рецепт с кодом —
  `references/bulk-view-sheet-operations.md`, рабочие скрипты — `scripts/del_sheets.csx`,
  `del_views.csx`, `del_templates.csx`, запуск — `scripts/runcsx.py <файл> compile|execute`.
- `status: broken` не вызывать вообще; `deprecated` — только при отсутствии замены и с пометкой в журнале.
- ElementId — Int32 (строковые ObjectId — там, где так указано в схеме), иначе молчаливое несовпадение.

## Нет подходящего инструмента → CSX, и это находка, а не обход

`quick_script_save` → `code_runner_compile` → `code_runner_execute` (в скрипте доступны `Doc`/`UIDoc`/`UIApp`,
выполняется в контексте Revit). Каждый обход каталога — **пробел каталога**: фиксируй отдельной строкой
отчёта (что нужно было сделать → чем закрыл), владелец репозитория пополняет плагин по таким отчётам.

## Клиент-прототип: снос моков и приведение контракта

Когда консоль/Electron-клиент писался против самодельного симулятора Revit, снос моков без
правки разбора ответа даёт «сломанный прототип» вместо чистого: симулятор отвечает MCP-стандартом
`{content:[…]}`, сервер — конвертом `{data}`. Установление контракта по коду сервера, порядок
правок, сборка верификации из `change_tracker_get_recent` + `get_parameters` и проверка
поведения без Revit — `references/mcp-client-contract-migration.md`.

## Ответ «доступен ли MCP X»: три разных статуса, не путай

Пользовательский вопрос «MCP UiController доступен?» — не бинарный. Различай и отвечай по факту:

- **Сервер жив** — доказано вызовом по HTTP (`get_document_info` / `get_ui_state` вернули данные).
- **Сервер подключён к Hermes** — проверяй блок `<имя>:` в `config.yaml` (`mcp_servers.*.enabled`). Это
  отдельная сущность: живой сервер может быть `enabled: false` и тогда его инструментов в твоей сессии нет.
- **Откуда взят инструмент** — при выключенном подключении работай по HTTP напрямую и говори об этом явно,
  а не создавай впечатления, что инструмент вызван штатным способом.

Правку `config.yaml` делает **пользователь**: Hermes режет запись в свой конфиг как security-sensitive
файл. Не пытайся обойти гейт повторными попытками — один раз упомяни, дай точный фрагмент блока с `enabled: true` и попроси
перезапустить сессию (без перезапуска новые MCP-инструменты не появятся).

**Идентифицируй продукт по его возможностям, а не по имени в каталоге.** В `tools/list` нет строк
`uicontroller`/`daemon`/`click`/`keyboard`/`mouse`, хотя сервер — именно UiController/RevitAiTools: узнаётся
по семейству UI-инструментов (`get_ui_state`, `capture_dialog_state`, `ui_set_dialog_auto_handle`,
`ui_get_dialog_settings`). Grep по имени продукта даёт ложный вывод «это не он». Полезный живой read-back
состояния — `get_ui_state` (документ, активный вид, лента, dialogAutoHandlers) и `capture_dialog_state`;
окно с title вроде `<guid>Monitor` — внутренний монитор демона, а не диалог Revit.

## Скриншот окна Revit: UIA там не работает, снимай через PrintWindow

Захват окна Revit через UI Automation **зависает**: главное окно Revit — WPF-обёртка
(`HwndWrapper[DefaultDomain;;<guid>]`), UIA-провайдер на нём не отвечает, и любая accessibility-захватка
падает по таймауту, хотя Revit рисуется нормально. Это свойство приложения, а не дефект контроллера:
не отлаживай дерево, а смени механизм захвата.

- **Бери `hwnd` окна Revit из перечня окон или `Get-Process | MainWindowTitle`, а не из только что
  упавшей accessibility-команды.** Скрипт ждёт именно hwnd: PID из `Get-Process Revit`
  он принимает за окно и падает с `GetWindowRect failed`.
- Снимай `PrintWindow` с `PW_RENDERFULLCONTENT` — скрипт `scripts/printwindow_capture.py` в навыке
  `windows-uia-automation` (`python printwindow_capture.py <hwnd> out.png --max-dim 1600`).
  Захват читающий: не поднимает окно, не перехватывает фокус, ничего не печатает в чужое окно.
- **Полноэкранный grab вместо этого вернёт перекрывающее приложение** (у пользователя поверх Revit
  может лежать Telegram) — это подтверждённый способ отдать правдоподобный снимок не того окна.
- **Проверь снимок глазами** (`vision_analyze`: что именно на картинке, какой документ и вид),
  а не по размеру файла; Revit-модель читается, обрезанный/пустой кадр — нет.
- Если нужен именно Revit-контент без риска для пользователя — комбинируй: скриншот через
  PrintWindow + чтение состояния через MCP (`get_ui_state`, `get_document_info`). Клики и ввод
  в окно Revit — только по явному разрешению, и SendInput бьёт в foreground.

## Аудит открытой модели только на чтение

Просьба «изучи модель, открытую в Revit» — это read-only проход, а не моделирование:
не вызывай write-инструменты и не правь модель пользователя. Порядок вызовов,
обязательные перекрёстные сверки (площади помещений, двери, объёмы, окна против
витражей) и работа с рендером — `references/model-audit-readonly.md`.

- **Клиент вызовов — `scripts/rpc.py`** (`python scripts/rpc.py <tool> ['{"a":1}']`,
  `list` печатает имена инструментов). Он передаёт тело файлом в NATIVE-пути и
  разбирает конверт MCP; инлайновый curl через `execute_code` упирается в MSYS-пути.

## Создание проверочного вида в чужой модели и разбор границ помещений

Просьба «создай план этажа, чтобы я кликнул и увидел границы» — это write в модель
пользователя, но явно запрошенный: пиши только осмотр (вид, рамка, детализация,
марки помещений), не трогай геометрию и параметры комнат без отдельной команды.
Пошаговый порядок, рабочие вызовы, проверенные ловушки API (`CropBox` без сдвига
камеры, `zoom_to_fit` как обязательный второй шаг, `capture_view` только для 3D,
`export_view_image` игнорирует `outputPath`) и диагностика «площадь не бьётся с bbox»
с порядком исправления — `references/inspection-view-and-room-boundaries.md`.
Перед руками по границам помни: `get_room_info.boundaryCount == 1` вместе с
завышенной площадью — признак периметра, натянутого через соседние комнаты.

## Каждый write подтверждай чтением (иначе это тихий отказ)

Инструмент вернул успех — доказательством это не является. После **каждого** write — независимое чтение:
сколько элементов стало, какие параметры, на месте ли геометрия. Запись без read-back в отчёт не попадает:
заявку «создал/изменил» делай только по результату чтения.
Журнал прогона — `tool_runs.jsonl`: имя инструмента, категория, tier, статус, sha1 аргументов, latency,
результат read-back. Из журнала считай покрытие (по каждой области ≥1 чтение и ≥1 запись) и дефекты —
памятью эти числа не собирай.

## Докажи, что в Revit твой код, до любой содержательной проверки

Сборка с `DeployIsolated` и строка «✅ N required files OK» **не доказывают**, что запущенный
Revit исполняет твой бинарник. Копирование в deploy-скрипте идёт с `-ErrorAction
SilentlyContinue`, поэтому заблокированные (уже загруженные Revit) файлы пропускаются молча,
без ошибки; проверка полноты — `Test-Path` на **существование**, а не на свежесть. Каталог
деплоя (`%LOCALAPPDATA%\RuBIMtech\ReVibe\plugins\revitCopilot\R<NN>`) общий для всех
worktree, поэтому его может занять сборка соседней ветки.

1. Сравни хэш `bin/Release.RNN/revitCopilot.dll` с задеплоенной. Расхождение — задеплоена не
   твоя сборка; иди к шагу 2, а не к «почему Revit не подхватил».
2. **Решающий признак — grep по строке-маркеру**, которой нет в старом коде: возьми
   идентификатор, который добавил твой срез (новое поле ответа или имя тула), и посчитай его
   в обоих бинарниках (`grep -c boundaryUnit a.dll`). Есть в твоём, отсутствует в
   задеплоенном — деплой утащил чужую сборку, и ни один вызов тула этого не покажет.
3. Формат ответа Revit — конверт `result{Data,IsSuccess}`, а **не** MCP `content[]`. Клиент,
   написанный по спецификации MCP, получит пустой результат, и это выглядит как «тул мёртв».
   Клиент обязан понимать обе формы.

**Отсутствие поля, которое эмитит твой текущий исходник, — не дефект кода, а признак чужого
бинарника.** Прежде чем «чинить» сервис, grep-ни оба бинарника по имени этого поля: пусто в
задеплоенном — вопрос к деплою, а не к коду.

Рецепт с командами, порядком обхода и признаками «деплой прошёл, а проверить нечего» —
`references/runtime-verification-deploy-provenance.md`.

## Известные особенности — проверяй их отдельными вызовами

Это готовый тестовый материал, а не справка: `create_wall.length` — толщина; `get_doors` может отдавать
нулевые размеры; `place_door` требует `doorTypeId`; у части инструментов стоит `status: broken` или
`deprecated`. Каждую ловушку прогоняй явно и записывай факт — так проверяется, что каталог не врёт.

## Тестовый стенд: модель-полигон

Требования конкретного полигона курса — `review/POLYGON_REQUIREMENTS.md` в репозитории курса; общий рецепт
«модель как стенд для прогона инструментов» (состав, намеренные дефекты, большая версия, негативные
проверки, гейты, формат отчёта о дефекте) — в `references/tool-test-harness.md`. Инварианты всегда:
работать в **своём** файле, а не в модели пользователя; модели не коммитить; builder делать идемпотентным
(повторный запуск даёт тот же результат — иначе прогон не воспроизводим).

## Гейты прогона

P1 состав модели · P2 идемпотентность builder'а · P3 покрытие доменов · P4 read-back после каждого write ·
P5 негативные проверки · P6 дефекты оформлены с минимальным воспроизведением · P7 минимум две версии
Revit · P8 найденное связано с уроками/документацией, которые на это опираются.

## Ловушки

- **Не выдавай отчёт об инструментах по памяти каталога.** Проверка «инструмент есть» — это `status` и
  факт вызова, а не строка в гайде: гайд отстаёт от плагина и наоборот.
- **Не пиши в модель одновременно из двух процессов** — один писатель на документ; параллельные прогоны
  дают конфликт транзакций и ложные «тихие отказы».
- **Не подменяй проверку инструмента проверкой своей логики:** если операцию сделал CSX, а не инструмент,
  в отчёте это два разных пункта — «инструмент не найден/сломан» и «результат получен обходом».
- **Считай 411/пустой ответ «сервер недоступен» только после проверки способа отправки.** На HTTPAPI без
  Content-Length это ошибка транспорта, а не сервера; повторная попытка тем же способом её не вылечит.
- **Мёртвый пид в порт-файле ≠ работающий сервер.** Каталог `%LOCALAPPDATA%\RevitAiTools\mcp` копится
  и не чистится: после нескольких сессий Revit в нём лежат файлы от давно закрытых процессов, и
  «файл есть» читается как «сервер есть». Проверяй живость pid (или сам `POST /mcp`) перед тем,
  как строить на этом вывод дальнейшую работу.
