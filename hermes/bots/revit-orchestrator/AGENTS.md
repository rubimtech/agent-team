## Внешние контуры (что должно быть поднято)

- **Revit MCP** — stdio-мост `.kilo/scripts/mcp-revit-bridge.cmd`; требует **запущенного Revit**
  с загруженным плагином ReVibe (R22–R27 в `%LOCALAPPDATA%\RuBIMtech\ReVibe\plugins\revitCopilot`).
  Инструменты: `capability_*`, `dll_list/dll_load/dll_reload/dll_unload`, `code_runner_*`, ~1340 тулов.
- **UiController MCP** (`ui`) — `{{LOCALAPPDATA}}\UiController\RevitUiController.McpServer.exe`,
  требует запущенного `RevitUiController.Daemon.exe --daemon`.
- **CodeGraph MCP** (`cgc`) — http://127.0.0.1:8104/api/v1/mcp/sse, docker profile `cgc`
  (`cd {{HARNESS_PLUGINS}} && docker compose --profile cgc up -d codegraphcontext`).
- **qdrant-kb** — коллекции `revit_api_knowledge`, `revit_api`, `Revit_SDK_Samples`, `navisworks_api_bge` (+3).
- **task_manager** — https://atm.apps.rubim.tech/mcp (агент команды регистрировать один раз, имя не плодить).

## Гейты

1. Нет RECON-блока и критериев приёмки — код не начинается.
2. Результат разработчика принимают QA + Reviewer, не разработчик.
3. Любой write в модель подтверждается чтением (read-back).
4. Тест на живом Revit — только в своём файле/полигоне.
5. Незакрытые пункты перечисляются прямо, без «готово».

# Правила для C# кода RevitAiTools

Всегда применяются. Частные исключения — в `docs/`, конкретные паттерны — в skills.

## Revit API
- Используй Nice3point.Extensions: `ToElement<T>()`, `FindParameter()`, `SetParameter()` вместо сырых `Cast<T>()` и `get_Parameter`
- Используй fluent-расширения из `FilteredElementCollector` вместо LINQ-фильтрации после загрузки
- Всегда оборачивай модифицирующие операции в `using Transaction`
- **MCP-тулы НЕ оборачивай в `ExternalEvent`.** Тело тула уже выполняется на потоке
  Revit — его туда диспетчеризует `IRevitTaskRunner` (ADR-007). Вызывай Revit API
  напрямую. `ExternalEvent` нужен только для modeless-окон, фоновых потоков и прочих
  вызовов вне API-контекста — см. skill `revit-external-events`

## Архитектура
- Разделяй логику на Tool → Service слои
- Используй DTO-преобразование перед возвратом данных из API
- Не используй `#if REVITxxxx` в бизнес-коде — только в `Modules/VersionCompat/`
- Не ссылайся на несуществующие пути (`Shared.Core/Models/`, `.kilo/references/revit-tools-catalog.json`) — проверь, что файл есть

## Обработка ошибок
- Оборачивай Revit API вызовы в try-catch с конкретными типами исключений
- Не подавляй исключения — логируй и возвращай понятную ошибку
- Для headless-режима используй FailureHandlingOptions

## Форматирование
- 4 пробела для отступа
- Фигурные скобки на новой строке (Allman style)
- `using` внутри namespace

# Restricted Files — файлы, которые НЕЛЬЗЯ читать

Следующие файлы содержат конфиденциальные данные и НЕ ДОЛЖНЫ быть прочитаны или изменены AI-агентом:

- `.env`
- `*.key`
- `credentials.json`
- `secrets.json`
- `appsettings.Local.json`
- `connection-strings/*.config`

Исключения:
- Если пользователь явно запрашивает работу с этими файлами — спроси подтверждение
- Не показывай содержимое в ответе
- Не логируй содержимое

# Правила параллельной работы

Дисциплина веток и PR для команды «человек + несколько AI-агентов», работающих над одним репозиторием.

## Ветки и PR

- Один агент — одна ветка. Агент не переключается между задачами в одной ветке.
- Одна ветка — один основной PR. Не добавляй новую фичу в открытый PR.
- Задачи, затрагивающие один критичный файл, выполняются последовательно.
- Агент явно указывает изменённые файлы. Это позволяет оценить пересечение.
- Перед началом работы агент проверяет активные PR в той же области.

## Зависимости между задачами

- Общие миграции БД не выполняются параллельно без координации.
- Конфликтующие задачи связываются через `blocked by`.
- После merge — обнови остальные ветки.

# Определение репозитория (оригинал vs форк)

Проект отделён от ReViBE. Агент должен определить, в каком репозитории он работает,
и выбирать поведение.

## Механизм определения (по приоритету)

1. `git remote get-url origin` — содержит `RevitAiTools` или `ReViBE`
2. Имя текущей папки — `RevitAiTools` или `ReViBE`
3. Наличие маркер-файла `.kilo/is-fork` (если есть — это форк)
4. Если ничего не совпало — спросить пользователя

## Репозиторий и поведение

### `rubimtech/RevitAiTools` (или `*/RevitAiTools`) — форк, наш проект
- Полная разработка: MCP-тулы, сервисы, модули, любые изменения
- `DATA/sp131.db` — копия из ReViBE, обновлять оттуда (см. задачу `sp131-db-usage.md`)

### `rubimtech/ReViBE` (или `*/ReViBE`) — оригинал, исходный ReViBE
- **Только чтение**: не менять файлы, не писать код
- Разрешено: анализ, code review, поиск дублей, исследование архитектуры
- Не трогать `Modules/`, `Shared.Core/`, `Shared.Services/` — там код ReViBE
- Если нужна правка — handoff в форк RevitAiTools

### Любой другой репозиторий
- Спросить пользователя, что это за репозиторий и ожидается ли разработка

# Режим «мой агент» vs «агент соавтора»

Проект поддерживает двух типов агентов. Агент должен определить свой режим в начале сессии.

## Как определить режим

1. Если пользователь явно сказал «ты мой агент», «работай со мной», «делай что я скажу» — режим **мой агент**
2. Если пользователь сказал «ты агент соавтора», «contributor», «fork» — режим **агент соавтора**
3. Если неясно — спросить пользователя: «Ты владелец репозитория или соавтор? В каком режиме работать?»

## Поведение

### Мой агент (работаю с владельцем)
- Полное доверие: работаю по прямым инструкциям пользователя
- Могу коммитить и пушить в свою рабочую ветку
- Merge в main — только по команде пользователя (он approve)

### Агент соавтора (contributor, другой человек)
- **Не коммитить и не пушить ничего в main**
- Работать только в task-ветке (не main)
- Все изменения — только через Pull Request
- PR не мёржить без явного approve от владельца
- Перед созданием PR показать diff и спросить разрешения
- Не удалять чужие ветки
- Не перезаписывать историю (rebase — только если PR ещё не создан)
